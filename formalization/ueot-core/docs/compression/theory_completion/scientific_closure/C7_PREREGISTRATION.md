## Declared object and candidate family

Physical implementation: actual local OS subprocesses speaking a line-oriented
request/response protocol over stdin/stdout.  The service candidate is a
majority router over a registered worker subset.

Registered nested candidates:

1. `W1` — one worker, quorum = 1;
2. `W1,W2` — two workers, strict majority quorum = 2;
3. `W1,W2,W3` — three workers, strict majority quorum = 2.

The C3 search claim is only minimality inside this registered nested family.

## Protocols

Two certification protocols with different intervention/information roles:

- `P_READ`: issue one logical request to every live worker; record per-worker
  reply, service majority reply, PID and latency.
- `P_SINGLE_FAULT`: terminate the last registered worker in the candidate, then
  issue the same request to surviving workers; the candidate passes iff the
  majority service still returns `OK`.  The process is reset before the next
  candidate/run.

Held-out perturbation:

- `P_REPLACE_HELDOUT`: in the three-worker service, terminate `W3`, create a
  fresh `W4` process, then run `P_READ` and `P_SINGLE_FAULT` against the new
  `{W1,W2,W4}` structure.  This is not inspected before the preregistration is
  frozen.

Negative control:

- `P_DOUBLE_FAULT`: terminate two workers from a three-worker service. Expected
  verdict: service unavailable / not certified.

Naive baseline:

- one-worker service under `P_SINGLE_FAULT`. Expected failure.

## Observable and estimator

Raw observation per request:

- UTC timestamp;
- run ID and split;
- protocol name;
- candidate/worker IDs;
- OS PID;
- worker reply/timeout/exit status;
- per-worker latency in nanoseconds;
- logical majority-service output;
- process replacement map when applicable.

Primary estimator is exact empirical pass/fail for each registered intervention
run.  No iid or asymptotic probability claim is made from this tiny pilot.

## Sample allocation

- discovery/method-development data: none from the certification run IDs;
- certification: 5 reset runs per candidate × each of `P_READ` and
  `P_SINGLE_FAULT`;
- held-out replacement: 5 reset runs on `{W1,W2,W4}`;
- negative control: 5 reset `P_DOUBLE_FAULT` runs;
- naive baseline: 5 reset one-worker `P_SINGLE_FAULT` runs.

Run IDs are generated by the script and split labels are immutable in raw JSONL.

## Stopping rule

No optional stopping. The script executes the complete registered run count or
records `EXECUTION_ERROR`. Missing runs are failures of the pilot execution, not
silently dropped observations.

## Error budget and thresholds

This local deterministic digital pilot uses exact logical response classification
rather than a statistical confidence interval:

- PASS requires every registered certification repetition to match the declared
  logical outcome;
- any contradictory certification repetition gives `REJECTED` for that local
  claim;
- execution/missing-data errors give `UNRESOLVED`, not PASS.

Latency is logged diagnostically and is not part of the pass threshold.

## Registered positive and negative controls

Positive:

- healthy three-worker `P_READ` succeeds;
- three-worker `P_SINGLE_FAULT` succeeds;
- held-out one-worker replacement retains the registered logical interface.

Negative:

- one-worker baseline under its only worker loss fails;
- three-worker `P_DOUBLE_FAULT` fails.

A negative control unexpectedly succeeding is a protocol/specification failure
and invalidates the corresponding claim rather than being reinterpreted as a
new success criterion.
